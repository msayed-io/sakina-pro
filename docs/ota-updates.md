# التحديثات الصامتة (OTA Live Updates)

> آخر تحديث: 2026-11-20 · البلوجن: `@capgo/capacitor-updater@8.54.2`

## الفكرة في سطر

تطبيق الأندرويد فيه طبقة ويب (`dist/`). عند كل تشغيل نتحقق من `version.json`
المرفق مع **آخر GitHub Release**. لو فيه نسخة أحدث: نُنزّلها في الخلفية ونجدولها
لتُطبَّق **عند خروج المستخدم من التطبيق أو التشغيل القادم**. لا واجهة، لا إشعار،
لا إعادة تحميل أمام المستخدم.

---

## الملفات المعنية

| الملف | الحالة | الدور |
|---|---|---|
| `src/services/otaUpdater.ts` | **جديد** | كل منطق OTA، معزول تمامًا (~200 سطر) |
| `src/main.tsx` | **+2 سطر** | استيراد + `startOtaUpdater()` قبل `createRoot` |
| `capacitor.config.ts` | **+4 أسطر** | `plugins.CapacitorUpdater.autoUpdate: false` |
| `ota/min-native-version.txt` | **جديد** | أرضية توافق الـAPK |
| `ota/README.md` | **جديد** | متى تُرفع الأرضية |
| `scripts/generate-ota-manifest.mjs` | **جديد** | يبني مانيفست البصمات من `dist/` |
| `.github/workflows/android-auth-callback.yml` | **خطوتا OTA فقط** | دفع `ota-bundle` + بناء الحزمة والبيان |
| `docs/ota-updates.md` | **محدَّث** | هذا الملف |

**لم يُلمس:** أي خطوة من خطوات بناء/توقيع/اختبار/رفع الـAPK. كل أسطر البناء
والتوقيع والاختبار والرفع (`assembleRelease`, `testDebugUnitTest`, `apksigner`,
`aapt`, `SHA256SUMS`, `gh release create`) عدد تكرارها **لم يتغير**. الأسطر
المحذوفة الوحيدة (17) كلها من خطوة OTA القديمة التي استُبدلت — ولا سطر واحد
منها يخص الأندرويد.

## دورة العمل

```
main → push
  │
  ├─ calculate-version        (كما كان تمامًا)
  ├─ signed-release
  │    ├─ build:android       → dist/
  │    ├─ cap sync android    → APK + AAB (كما كان تمامًا)
  │    ├─ [جديد] zip dist → dist.zip + version.json (بالـ checksum)
  │    └─ gh release create   → APK + AAB + SHA256SUMS + dist.zip + version.json
  │
  └─ الجهاز: عند التشغيل → يقرأ version.json → ينزّل → يجدول → يُطبِّق عند الخروج
```

## مخطط الإصدار (مهم — كان هنا عيب قاتل)

`version.json.version` = **إصدار الإصدار + رقم التشغيل**: `X.Y.Z.<run_number>`
مثال: الإصدار `v2.3.46` ← الحزمة `2.3.46.451`.

### لماذا لا يكون نفس رقم الإصدار؟

الحزمة المدمجة داخل الـAPK تحمل `versionName` الـAPK نفسه (`2.3.46`). فلو كان
`manifest.version = "2.3.46"` لكانت المقارنة:

```
compareVersions("2.3.46", "2.3.46") === 0  ←  لا تنزيل، أبدًا
```

أي أن **كل** جهاز على APK `v2.3.46` كان سيرفض كل تحديث ويب لنفس الإصدار —
فشل صامت مع CI أخضر. الجزء الرابع `run_number` يضمن
`2.3.46.451 > 2.3.46` فيُطبَّق التحديث، ويضمن أيضًا أن رقم تشغيل أحدث يتقدّم
على رقم أقدم (`2.3.46.452 > 2.3.46.451`).

### الشرطان اللازمان معًا

1. **`otaUpdater.ts` يجب أن يقارن كل الأجزاء الرقمية** (لا ثلاثة فقط). لو قصّ
   `parseVersion` إلى `major.minor.patch` لصارت `2.3.46.451` مساوية لـ`2.3.46`
   وعاد العيب نفسه. `compareVersions` الحالي يفصل جميع الأجزاء.
2. **رابط التنزيل يستخدم الوسم الحقيقي `RELEASE_TAG`** (`v2.3.46`)، **لا**
   رقم الحزمة. لو استخدم `v2.3.46.451` لكان 404 لأن الوسم المنشور `v2.3.46`.

> مرفوض: `1.0.${run_number}` — يبدو دائمًا أقدم من `2.3.x` فيسقط صامتًا.

## الحقول الثلاثة الحرجة في `version.json`

```json
{
  "version": "2.3.46.451",
  "url": "https://github.com/msayed-io/sakina-pro/releases/download/v2.3.46/dist.zip",
  "checksum": "<sha256 hex لـ dist.zip>",
  "minNativeVersion": "2.3.46"
}
```

- `version` يحمل 4 أجزاء (`X.Y.Z.run`) — انظر «مخطط الإصدار» أعلاه.
- `url` يحمل الوسم `vX.Y.Z` بثلاثة أجزاء فقط (الوسم الحقيقي المنشور).

**`checksum` إلزامي** — ليس اختياريًا. البلوجن يرفض أي تنزيل بلا checksum
(`requireBundleChecksum` → `IOException: Checksum required`). كان هذا سيُسقط
التحديث كله بصمت لو لم يُضف.

## الحمايات

| الخطر | الحماية |
|---|---|
| حزمة معطوبة تُقفل التطبيق | `notifyAppReady()` فور الإقلاع؛ بلا استدعاء يتراجع البلوجن تلقائيًا |
| ويب جديد على APK قديم | `minNativeVersion` يُقارن بـ `current().native` قبل التنزيل |
| التراجع لإصدار أقدم | مقارنة SemVer (`compareVersions`) لا `!==` |
| فحصان متزامنان | قفل `inFlight` |
| إعادة تحميل في وجه المستخدم | `next({id})` لا `set({id})` |
| ظهور على الويب (Vercel) | `Capacitor.isNativePlatform()` + خروج مبكر |
| أي خطأ يعطّل الإقلاع | كل شيء داخل `try/catch` صامت؛ الدالة `void` |
| عودة بعد 6 ساعات | فحص هادئ عند `visibilitychange` |

## أرضية التوافق — `ota/min-native-version.txt`

**ارفع الرقم فقط** عند: إضافة/حذف بلوجن أصلي، تغيير `applicationId`، أو أي سطح
أصلي جديد تعتمد عليه طبقة الويب. **لا ترفعه** لتعديلات React/الويب العادية —
وإلا تجمّد التحديث الصامت لكل من على APK أقدم.

القيمة الحالية `2.3.45` = أول APK يحتوي بلوجن التحديث. لا ترفعها إلا حين يلزم
ويب جديد على APK أحدث فعلًا.

## التحديث التفاضلي — المسار الأساسي

الحزمة الكاملة `dist.zip` تزن ~92 MB، ومعظمها فيديوهات وبيانات لا تتغير بين
إصدارات الويب. لذلك لا نُنزّلها في كل تحديث.

```
التطبيق                      GitHub
   │                            │
   ├── GET version.json ───────►│  raw.githubusercontent.com
   │   (CapacitorHttp، بلا CORS) │  /ota-bundle/version.json
   │◄── { version, manifest } ──┤
   │                            │
   ├── getMissingBundleFiles ──►│  مقارنة محلية بحساب
   │   (بلا شبكة)               │  ota-builtin-hashes.json
   │                            │  + كاش الحزم
   │◄── { missingCount } ───────┤
   │                            │
   ├── download({ manifest }) ─►│  الملفات الناقصة فقط
   │◄── bundle.id ──────────────┤  (عادةً بضعة KB)
   │                            │
   └── next({ id })             │  يُطبَّق عند الخروج/التشغيل القادم
```

### من أين يُقرأ البيان؟ (سبب عطب v2.3.47)

**العطب:** حتى `v2.3.48` كان البيان يُقرأ بـ`fetch()` من:

```
https://github.com/msayed-io/sakina-pro/releases/latest/download/version.json
```

هذا الرابط يرد بسلسلة **302 مزدوجة**:
`github.com` → `github.com/releases/download/<tag>/…` →
`release-assets.githubusercontent.com`، **ولا يحمل أي منها
`Access-Control-Allow-Origin`**. صفحة الويب تعمل على أصل `https://localhost`،
فـWebView يرفض القراءة ويُطلق `TypeError: Failed to fetch` قبل أن يصل الجسم
إلى JS. الخطأ كان يُبتلع في `catch`، فبدا التحديث «صامتًا» إلى الأبد:
لا تحديث، ولا رسالة، ولا أثر.

المفعول على الجهاز: التنزيل **لم يبدأ أصلًا**، فلم تُكتب أي حزمة، ولم يجد
البلوجن ما يطبّقه عند الخروج — ولهذا لم يظهر إصدار الويب الجديد بعد
إعادة التشغيل.

**الإصلاح:** مساران، كلاهما عبر `CapacitorHttp` (طبقة Java/OkHttp الأصلية
خارج محرّك الويب، فلا تُطبَّق سياسة أصل إطلاقًا):

1. **الأساسي:** `raw.githubusercontent.com/.../ota-bundle/version.json` —
   نفس الفرع الذي تُنزَّل منه كل الملفات، ويُقدَّم بترويسة CORS صالحة.
   نشرُه يتم في الـworkflow بعد دفع الملفات (انظر `Publish OTA manifest`).
2. **الاحتياطي:** رابط الـRelease نفسه — ينجح عبر الطبقة الأصلية لأن
   `HttpURLConnection` يتبع الـ302 افتراضيًا، ولأن CORS لا ينطبق عليها.

> `version.json` كان يُحذف عمدًا من فرع `ota-bundle` قبل `v2.3.49`، فكان
> المصدر الوحيد هو رابط الـRelease — وهو تحديدًا ما يكسره CORS. لذلك لم
> يعمل الاحتياطي وحده كحلّ: المصدر الأساسي يجب أن يكون CORS-safe.

### متى تُطبَّق الحزمة؟

البلوجن ينفّذ التطبيق من `appMovedToBackground()` **فقط**
(`CapacitorUpdaterPlugin.java:5909`). لو اكتمل التنزيل بعد أن صار التطبيق في
الخلفية، لا يصل حدث خلفية آخر، ويبقى `next` معلّقًا في SharedPreferences —
و**لا شيء يقرأه عند الإقلاع البارد**. من هنا: قتل التطبيق بالسحب قبل أي دورة
حياة تالية يُضيّع التطبيق (لا الحزمة).

لذلك بعد نجاح `next()` يطلب `otaUpdater` صراحةً `reload()` في اللحظة التي
تصبح فيها الصفحة `hidden`. البلوجن يطبّق `next` المعلّق ثم يعيد التحميل وهو
**خلفي** (`_reload()` → `reloadInBackground()`، سطر 3274)، ويثبّت الحزمة في
`CAP_SERVER_PATH` عبر `setCurrentBundle()` (`CapgoUpdater.java:1698-1703`)
فتصمد أمام القتل وإعادة الفتح. فحص `notifyAppReady` المؤجّل يتجاهل العمل
وهو في الخلفية (`runDeferredAppReadyCheck`، سطر 5780)، فلا يتسبب `reload()`
في أي تراجع.

### كيف تُقرَّر «الملفات الناقصة»؟

البلوجن يقرأ `android/app/src/main/assets/public/ota-builtin-hashes.json` —
ملف يكتبه **`cap sync` تلقائيًا** (hook مدمج في البلوجن) ويحوي SHA-256 لكل
ملف مدمج في الـAPK. أي ملف بصمته في المانيفست تطابق بصمته المدمجة **يُعاد
استخدامه بلا تنزيل**. الملفات المتغيرة فقط تُسحب من فرع `ota-bundle`.

هذا يعني أن أول تحديث بعد تركيب APK جديد يكون صغيرًا جدًا؛ وبعد أول OTA
يصبح الكاش المحلي هو مصدر إعادة الاستخدام.

### التسلسل الإلزامي في CI (منع سباق 404)

1. `npm run build` → `dist/`
2. **دفع `dist/` إلى فرع `ota-bundle`** (فرع يتيم، `--force`)
3. بناء `dist.zip` وحساب بصمته
4. توليد `version.json` بالسكريبت
5. `gh release create` يحوي `dist.zip` + `version.json` + APK + AAB

بهذا الترتيب يستحيل أن يقرأ جهاز إصدارًا جديدًا قبل توفّر ملفاته.

### المسار الاحتياطي

`dist.zip` يبقى شبكة أمان. يُستدعى فقط إذا: غاب `manifest` من البيان، أو فشل
`getMissingBundleFiles`/`download` التفاضلي لأي سبب (شبكة، بصمة، ملف تالف).
في الحالتين التنزيل يجري بصمت ولا يرى المستخدم شيئًا.

### لماذا `minNativeVersion` مهم هنا؟

التحديث التفاضلي يفترض أن الملفات غير الموجودة في المانيفست موجودة في الـAPK.
لو كان الـAPK أقدم من الأرضية المعلنة، قد تكون ملفات ناقصة. الحاجز يمنع ذلك
قبل أي تنزيل.

## اختبار يدوي على جهاز (لم يُنفَّذ — لا جهاز متاح)

1. ثبّت APK إصدار `2.3.45` أو أحدث.
2. افتح التطبيق، استخدمه دقيقة، ثم أغلقه كليًا (من قائمة التطبيقات).
3. ادفع تعديل ويب إلى `main` وانتظر CI ينشر إصدارًا جديدًا (مثال `2.3.46`).
4. افتح التطبيق، استخدمه، **ثم اخرجه للخلفية** (لا تُغلقه).
5. أعد فتحه → يجب أن يظهر تعديل الويب الجديد.
6. تحقق من السجلات: `adb logcat -s CapgoUpdater` يجب أن يُظهر `download` ثم `next`.

**اختبار التراجع:** ارفع حزمة معطوبة عمدًا (احذف `index.html` قبل الـzip) — يجب
أن يعود التطبيق تلقائيًا للحزمة الأصلية في التشغيل التالي بدلًا من التعطل.

## مخاطر متبقية

- **لا توقيع للحزمة** — التحقق SHA-256 يكشف النقل التالف لا التلاعب الخبيث؛
  الاعتماد على HTTPS + GitHub.
- **التنزيل عند الإقلاع** — يستهلك بيانات في أول فتح بعد كل إصدار (صامت لكنه
  غير مجاني).
- **شاشة الإقلاع** — التنزيل يبدأ فورًا بعد `createRoot`؛ لا يؤثر على زمن الظهور
  لأن كل شيء غير متزامن وغير محجوب.
